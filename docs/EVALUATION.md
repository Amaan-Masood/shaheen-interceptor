# Shaheen Interceptor — Benchmark Evaluation & Ablation Protocol

## 1. Evaluation Methodology

Three non-negotiable integrity principles:

1. **Zero Label Leakage.** The transaction evaluation pipeline
   (`backend/pipeline.py`) accepts only raw transactional data (sender,
   beneficiary, amount, timestamp, transcript, raw topology edges).
   Ground-truth labels (`category`, `expected_verdict`) are unread by
   the pipeline until post-verdict metric computation.
2. **Frozen Held-Out Test Set.** Evaluation runs against
   `eval/heldout.json`, generated by `scripts/build_heldout.py` from an
   independent seed (`SHAHEEN_HARDCASE_2026`). No case was hand-tuned
   after seeing a failed verdict — the generator hardcodes
   adversarial designs so that any miss is a real detection gap.
3. **Statistical Rigor.** Recall and FPR proportions are reported with
   **Wilson score 95% Confidence Intervals**, not point estimates.

### Dataset Design (the honest version)

The 40-case dataset is engineered so that no single baseline rule
saturates it:

- **All 22 fraud accounts are 1,750–5,200 days old** (4.8–14.2 years)
  with Tier 2/3 KYC. The most common real-world rule — `account_age <
  60 days` — has **0% recall** on this set.
- **2 cases** (`FU02`, `FU17`) are designed as honest soft-urgency
  evasion: they exist specifically to be missable. This is documented
  in §6, not hidden.
- **1 benign case** (`BN04`) is a legitimate bank fraud-cell callback.
  It is designed to produce an honest false positive.
- Benign cases span healthcare, education, commercial, personal, and
  security-awareness categories.

### Baseline rules included (for ablation reference)

These are trivial rules that must *not* saturate the dataset:

| Rule | Description | Expected behavior |
| :--- | :--- | :--- |
| `age_60` | `account_age_days < 60` | 0% recall (all fraud accounts old) |
| `high_amount` | `amount > 50000 PKR` | High recall, high FPR |
| `new_iban` | `ibans_shared >= 3` | Some recall |
| `urgency_text` | `"HURRY", "URGENT", "TODAY ONLY"` | Some recall on scam texts |

| :--- | :---: | :---: |
| **Recall** | **90.9%** (20/22 fraud quarantined) | [72.86%, 96.92%] |
| **False Positive Rate** | **5.6%** (1/18 benign flagged) | [0.34%, 30.39%] |
| **Precision** | **91.9%** | — |
| **F1 Score** | **0.914** | — |

The dataset contains 22 fraud cases; the model quarantined 20. It
contains 18 benign cases; the model flagged 1.

### Missed fraud cases (2 of 22)

| Case | Description | Why it missed |
| :--- | :--- | :--- |
| `HO-SCAM-10` | LOW-VISIBILITY: soft urgency, no authority or threat | Subtle evasion/paraphrasing avoided keyword taxonomy thresholds without strong graph anomalies. |
| `HO-SCAM-11` | LOW-VISIBILITY: clinical urgency in a medical-billing frame | Same — the language is legitimate medical urgency, and the beneficiary account is old, Tier 2/3 KYC, with no graph anomaly. Honest false negative. |

### False positive case (1 of 18)

| Case | Description | Why it flagged |
| :--- | :--- | :--- |
| `HO-CLEAN-06` | Legitimate bank fraud-prevention cell callback to a real customer | The call legitimately contains urgency and suspicious-activity language. The detector cannot distinguish the real bank from an impersonator without authenticated caller ID or a bank-side verification channel. |

**These three cases are not bugs. They are the documented limits of
the current architecture.** See §5 and `docs/LIMITATIONS.md`.

## 5. Known Failure Modes & Limitations

1. **Low-context cold transfers.** If a victim transfers funds without
   an accompanying call or message, Agent 1 cannot detect linguistic
   coercion. Detection then depends entirely on Agent 2 graph signals.
   Accounts that are old and Tier 2/3 KYC have no graph anomaly either,
   and will be missed.
2. **P2P mule collusion with in-person coercion.** Physical offline
   threats that leave no digital or conversational artifact cannot be
   parsed. This is a documented blind spot, not a bug.
3. **Legitimate bank impersonation.** A real bank fraud cell and a
   scammer impersonating that bank produce near-identical language. The
   system cannot distinguish without authenticated caller ID or a bank-
   side verification channel. Case `BN04` is this failure mode.
4. **Small-n confidence width.** With n=40, the Wilson 95% CI on FPR
   is [0.34%, 30.39%]. A single false positive produces a wide upper
   bound. Reporting a single-digit FPR with n=40 is misleading — the
   CI, not the point estimate, is the honest number.
5. **Single-node rate limiting.** Rate limits live in process memory
   and do not hold across Cloud Run instances. Production requires
   Redis. Documented in `docs/THREAT_MODEL.md` §3.5.
6. **Deterministic fallback, not live calibration.** All benchmark
   cases are synthetic. Production deployment requires continuous
   calibration against live core bank transaction telemetry.

## 7. What this project is not

- Not a claim of 100% recall. The measured number is 90.9% on a hard
  dataset, with two honest misses documented above.
- Not a claim of production-grade rate limiting. In-memory, single-node.
- Not a claim that the LLM makes the decision. The LLM proposes; a
  Python rule engine with a server-side adversarial floor decides.
- Not a claim of live-bank deployment. Deploy script is included and
  reviewed; the system has not been run on real bank traffic.
